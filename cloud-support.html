02 · Deployment

A reviewed change becomes a live release

  1. Change the sourceCreate a Git branch and pull request with a clear description of the change.
  2. Run checksCheck the application contracts, unit tests and dependencies. Keep private credentials out of browser code.
  3. Review the previewVercel builds the candidate. Inspect its desktop and mobile layouts and test the affected interactions.
  4. Merge and deployA reviewed merge to the connected main branch triggers the production deployment.
  5. Verify productionCheck the live URL, archive and graph. Match the revision returned by the health endpoint to the intended commit.
  6. Recover if necessaryUse Vercel’s deployment controls to return to a known working release, then repeat the health and user-flow checks.

Source: GitHub Actions, release guide and production checks. Recovery is an operator action.

03 · Cloud support

Locate the failure before changing the system

Start with the affected page and action. Use public health checks to locate the failing layer, then inspect the corresponding deployment or server logs.

01Archive unavailableThe page opens, but shared records do not load.

Check health and the archive response. Inspect database connectivity and deployment configuration in the operator dashboard. The local cabinet can remain available while the shared archive is unavailable.

02Generation failsExisting ideas load, but a new request fails.

Inspect the request’s response and the Vercel function logs. Check model configuration, quota or admission limits. Correct the failing dependency, then retry deliberately. Browsing existing records does not require a generation request.

03Wrong version appearsThe page does not match the intended release.

Compare the health response’s revision with the reviewed commit. Confirm that the production domain points to the intended Vercel deployment, then refresh the page and check the changed feature.

04A release regressesA previously working action now fails.

Record the failing action and release revision. Inspect the checks and logs. Recover to a known working deployment when needed, then confirm the archive, card drawer, graph and affected action. A green build alone does not establish runtime health.

Health ↗Status ↗Readiness ↗Report an issue ↗

For a useful support report, include the time, page, action, expected result, observed error and release revision. Keep credentials and private payloads out of the report.
